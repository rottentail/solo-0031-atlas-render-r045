# 运行与恢复

## 进程形态

服务只有一个可执行文件：`atlas`。两种子命令：

- 无参数：运行服务。
- `atlas check -mode live|ready [-url URL] [-timeout 3s]`：探测本机实例，输出一行 JSON 并以退出码报告结果。`live` 只问进程是否在服务 HTTP；`ready` 还要求状态卷可写且状态由本进程独占。默认地址取自 `ATLAS_ADDR`，指向自身回环地址。

环境变量：`ATLAS_ADDR`（默认 `127.0.0.1:8763`，容器内应设 `0.0.0.0:8763`）、`ATLAS_STATE`（默认 `var/atlas-state.json`）。状态目录必须是运行用户可写的独立卷；代码目录不需要写权限，容器镜像以只读根文件系统运行。

退出码：

| 码 | 含义 |
|---|---|
| 0 | 正常停止（收到 SIGTERM/SIGINT，HTTP 已排空） |
| 1 | 配置、监听或其它致命错误 |
| 2 | `check` 用法错误 |
| 3 | 同一状态路径已被其它进程独占，本实例拒绝运行 |

## 容器部署

```sh
docker build -f deploy/Dockerfile -t atlas-render:0.1 .        # distroless 非 root
docker build -f deploy/Dockerfile.local -t atlas-render:dev .   # 无 registry 时的本地替代
docker compose -f deploy/compose.yaml up -d
```

镜像要点：

- 两阶段构建，运行镜像只含静态二进制（`CGO_ENABLED=0`），没有 shell、包管理器或源码。
- 以非 root 运行（distroless `65532`）。状态卷必须由该 uid 可写；镜像在 `/var/lib/atlas` 预建了该属主的空目录，新命名卷会继承它。已有卷若由 root 创建，需显式 `chown 65532:65532`。就绪失败而存活正常正是该前置条件未满足时的表现。
- `ATLAS_STATE=/var/lib/atlas/state.json` 位于命名卷 `/var/lib/atlas`，是唯一可写路径。镜像内置 `VOLUME`，compose 用命名卷 `atlas-state`。
- `read_only: true` 与 `tmpfs /tmp`。代码与镜像层只读，状态只落在卷上。
- 容器健康检查用 `atlas check -mode live`，即存活探针。就绪探针单独使用 `/readyz`（Kubernetes 的 `readinessProbe` 同理）：卷不可写时容器**不应**被重启。
- `stop_grace_period: 20s` 覆盖 15 秒 HTTP 排空加最多 10 秒执行循环退出。

### 存活与可接收工作

| 端点 | 200 的条件 | 用途 |
|---|---|---|
| `GET /healthz`、`GET /livez` | 进程在服务 HTTP | 容器存活探针；不触碰数据卷 |
| `GET /readyz` | 状态已打开、锁归本进程、状态目录当前可写 | 就绪探针、负载均衡摘流 |
| 业务 `/v1/*` | 同上 | 未就绪时返回 503，`code` 为 `state_locked`、`state_invalid`、`state_unusable` 或 `state_commit_failed` |

`/readyz` 在 503 时返回 `{"status":"not_ready","reason":...,"error":...,"statePath":...}`。`reason` 区分：`state_locked`（另一实例持有卷）、`state_unusable`（权限、只读卷、路径不可用）、`state_invalid`（持久数据损坏或不支持版本）、`state_commit_failed`（提交未落盘）。

进程启动时先监听端口，再尝试打开状态；打开失败不会退出，而是每 2 秒重试，期间存活正常、就绪失败、业务返回 503。这样卷权限或挂载问题表现为明确的“活着但不能工作”，而不是崩溃循环。运行中状态目录变为只读时，就绪探针在 1 秒缓存窗口内转为失败；已渲染但未能提交的结果保留在内存中并持续重试，不会永久悬挂或丢失。

唯一的例外是**运行中**发现锁被其它进程取得：本实例立即停止，避免两个写者。

## 独占与误挂同一目录

`persist.Open` 先取 `state.json.lock` 的 `flock` 排他锁，再读取状态。第二个进程（同一主机上的两个容器，或两个挂同一卷的实例）拿到 `ErrLocked`，以退出码 3 失败，并在日志中给出锁文件路径与记录持有者。锁文件可长期存在；锁的有效性由操作系统文件锁决定，删除锁文件不能绕过。持有者在锁文件中写入 `pid=... started=...`，仅作诊断：容器内 PID 与主机不同。

限制：`flock` 在单一内核内有效。跨主机共享文件系统（NFS 等）或无法传递锁的存储不做保证；不要把同一状态卷同时挂到两台主机。

## 停止、强制终止与恢复

- SIGTERM/SIGINT：停止领取任务，取消执行中的计算，排空 HTTP（≤15 秒），等待执行循环退出（≤10 秒），释放锁后退出 0。执行中的任务在持久状态中仍为 `running`。
- SIGKILL：不做清理。状态文件始终通过“临时文件 → `fsync` → 原子替换”提交，因此卷上只会残留 `.atlas-write-*` 临时文件，不会出现半写状态。
- 下一次启动：在持锁状态下删除残留临时文件，校验持久数据，把 `running` 任务改回 `queued`（attempt 不变）并重新执行，使用固定输入与固定快照，而非最新场景。
- 已提交的收据、任务、快照和结果字节都在卷中；同键重放跨重启、跨强制终止仍返回原任务。

这些行为由 `python3 scripts/container_lifecycle.py` 用真实进程验证：只读代码树、独立状态卷、SIGTERM、SIGKILL、重启、双实例冲突、只读卷就绪失败与恢复。脚本以普通用户运行，需要 Go 工具链构建；在无容器运行时的环境中，它证明的是同一进程生命周期契约，不能替代目标运行时的冒烟测试。

## 备份与演练

先正常停止实例，复制状态 JSON 及锁文件之外的全部卷内容；恢复时复制到空的独立状态路径再启动。不要把运行中手工编辑的 JSON 作为新事实。启动校验拒绝不支持版本、损坏摘要、孤立关联和非法文档，并以退出码 1 或就绪失败报告。备份包含 PNG 字节与全部快照引用闭包，无需外部素材服务。

## 容量与观察

`GET /v1/status` 报告未压缩的结果 PNG 字节总量和各任务状态计数，不代表堆内存峰值。完整状态在事务中复制并编码，长期积累会增加提交成本。当前未提供任务或快照删除；按预期数据量规划卷容量与实例周期。结果清理只删除 PNG 字节。历史事件超过 500 条会截断，`sequence` 继续增加。

## 故障处置

- 保留状态卷与服务日志，在副本上检查；不要手工改卷内 JSON。
- 503/500 表示事务未完成；先读原请求目标确认状态。
- 提交任务使用稳定幂等键，不能因连接中断换键。409 结合场景 revision、快照 state 或收据语义判断；410 表示成功结果字节已清理，任务成功事实仍保留。
- 退出码 3 表示误挂同一卷：确认另一个实例的归属，不要删除锁文件或并行启动。

`deploy/atlas.service` 仍是 systemd 示例，需按实际用户、二进制和状态路径调整。macOS 可直接运行同一二进制。跨进程共享写入、跨机器文件系统锁和网络存储未经验证。
